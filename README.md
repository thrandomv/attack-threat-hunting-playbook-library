## Why this repository is different

Most public detection libraries are collections of queries. A query is an assertion: it claims that
a pattern means something, and nothing in the repository ever tests that claim. This one is built to
be falsifiable.

**Every Sigma rule has unit tests.** Synthetic events assert that each rule fires on the behaviour it
claims to detect *and stays silent on the benign lookalike that motivated its tuning note*. The tests
run in CI in under a second, with no SIEM and no licence, using a Sigma evaluation engine included
in this repository ([`scripts/sigma_eval.py`](scripts/sigma_eval.py) — standard library only, apart
from PyYAML for reading the rule files). It is not a toy: it implements field modifiers, the condition grammar, and correlation rules
(`event_count`, `value_count`, `temporal`), and it refuses to evaluate constructs it does not
support rather than silently passing them. It caught a malformed condition in this library's own
PowerShell rule during authoring.

**Every claim is checked against source data.** ATT&CK technique IDs, tactic assignments and
Detection Strategy references are validated against a pinned snapshot of the official MITRE STIX
bundle. Atomic Red Team GUIDs are validated against a pinned snapshot of the upstream index. Both
snapshots are regenerated by scripts in this repository, so a technique that was renumbered or a
test that was withdrawn upstream becomes a build failure — not a footnote someone notices in an
interview.

**Every playbook states what it misses.** Each has a "Limitations and blind spots" section that names
the evasion that defeats it. Where Atomic Red Team publishes no test for a technique, the playbook
says so and provides a manual validation procedure instead of inventing a GUID.

**Everything derived is generated.** The coverage table below, the ATT&CK Navigator layer, the
coverage matrix and the legacy-ID map are produced from playbook frontmatter by
[`scripts/build.py`](scripts/build.py). CI fails if they drift.

## Quick start

```bash
git clone https://github.com/thrandomv/attack-threat-hunting-playbook-library.git
cd attack-threat-hunting-playbook-library
pip install -r requirements-dev.txt

make test        # run the Sigma unit-test suite (160 cases)
make selftest    # verify the evaluation engine itself (42 checks)
make validate    # structural, schema, ATT&CK and Atomic validation
make check       # everything CI runs
```

Then, to use the content:

1. Read the [deployment guide](docs/DEPLOYMENT.md) and [telemetry requirements](docs/TELEMETRY.md).
2. Pick one playbook whose **required** telemetry you actually have. Verify that with the
   data-quality check in its "Telemetry requirements" section — not by assumption.
3. Run its KQL over a short lookback and read the raw results before scheduling anything.
4. Baseline the tunable parameters against your own data using the companion queries included in
   most `.kql` files, then apply local allowlists per the [tuning methodology](docs/TUNING.md).
5. Validate with the mapped Atomic Red Team tests in a lab ([validation strategy](docs/VALIDATION.md)).
6. Record coverage, exceptions, owner and review date in your detection register
   ([operating model](docs/OPERATING_MODEL.md)).

## ATT&CK v19 and what changed

This library targets **Enterprise ATT&CK v19.2**. v19 restructured the matrix in ways that break
older content:

- The Defense Evasion tactic was replaced by **Stealth (TA0005)** and **Defense Impairment (TA0112)**.
- `T1562.001` (Impair Defenses: Disable or Modify Tools) became **`T1685`**.
- `T1070.001` (Clear Windows Event Logs) became **`T1685.005`**.
- `T1557.001` was renamed to *Name Resolution Poisoning and SMB Relay*.
- ATT&CK now publishes **Detection Strategies** (`DET####`) and **Analytics** (`AN####`) with
  explicit *mutable elements* — the parameters an implementer is expected to tune.

Each playbook maps to its Detection Strategy and turns those mutable elements into a concrete
tunable-parameter table, so ATT&CK's guidance and this content stay in sync rather than merely
citing each other. The full revoked-ID table is generated at
[`mappings/legacy-technique-ids.md`](mappings/legacy-technique-ids.md).

## Quality standard

A match is a lead, not a verdict. Every default threshold in this repository is visible, named, and
documented as something to baseline locally — thresholds copied from a public repository are
someone else's environment's opinion.

No content here ships as `production` status. That status is earned in one specific environment,
against its own baseline, with an owner and a review cadence. The library ships `hunt` and
`production-candidate` content and tells you what to measure before promoting it.

# Purple-team validation with Atomic Red Team

## Principle

A detection you have never triggered is a hypothesis. Atomic Red Team provides small, documented,
reproducible tests for ATT&CK techniques, which makes it the cheapest way to turn a hypothesis into
evidence — and, just as often, to discover that a rule was never going to fire because the telemetry
it needs is not being collected.

## How this repository uses it

Each playbook lists Atomic tests by **GUID** in its frontmatter and in a "Purple-team validation"
table that states, per test, what evidence you should expect to see.

Those GUIDs are validated in CI against
[`validation/atomic-index.json`](../validation/atomic-index.json), a pinned snapshot of the upstream
Atomic Red Team index generated by `scripts/fetch_atomic_index.py`. A GUID that does not exist
upstream fails the build. This is deliberate: a fabricated or stale test reference is worse than no
reference, because it invites a reader to trust a validation path that does not exist.

The generated coverage table lives at
[`validation/atomic-coverage.md`](../validation/atomic-coverage.md).

## Where there are no tests

Atomic Red Team does not cover everything. `T1027.010` (command obfuscation) has no published tests
at all, and `T1505.003` (web shell) has one that covers file placement but not execution. Those
playbooks say so explicitly and provide a manual validation procedure instead. Stating a gap is part
of the deliverable; papering over it with an unrelated GUID is not.

## Safety rules

These tests execute real techniques. Several of them are destructive or produce genuine credential
material.

1. **Lab only, or an explicitly authorised test window with a change record.** Never on production
   without written approval and a rollback plan.
2. **Never run credential-dumping or replication tests against production Active Directory.** The
   material they recover is real.
3. **TH-024's tests destroy recovery points.** Run them on a disposable host you are prepared to
   rebuild.
4. **TH-018's spraying tests cause account lockouts** and are indistinguishable from an attack to
   anyone else watching. Use a lab tenant and dedicated test accounts.
5. **TH-022's coercion tests can disrupt authentication** on a domain controller.
6. **Clean up.** Each atomic defines a cleanup command; run it, then verify.

## A validation run that is worth recording

For each test, capture:

| Field | Example |
|---|---|
| Playbook / rule | TH-024 |
| Atomic GUID | `43819286-91a9-4369-90ed-d31fb4da2c01` |
| Authorisation | Change CHG-2026-0912, lab scope, approved by SOC lead |
| Executed | 2026-09-12 14:02 UTC, host LAB-WIN-07 |
| Telemetry observed | `DeviceProcessEvents` at 14:02:04 (4s latency), command line intact |
| Rule outcome | Alert raised 14:02:41; entities mapped: host, account, process |
| Gaps found | System channel not forwarded from lab hosts; 7045 absent |
| Follow-up | Enable System channel collection; re-test |

The "gaps found" row is usually the most valuable line in the table. A validation run that finds
nothing has told you less than one that finds a collection hole.

## Interpreting the outcome

| Outcome | Means | Next step |
|---|---|---|
| Test ran, alert raised | The detection path works end to end | Record and move on |
| Test ran, telemetry present, no alert | The rule logic or thresholds are wrong | Reproduce the event as a unit-test fixture, fix the rule, keep the fixture |
| Test ran, no telemetry | A collection or audit-policy gap | Fix collection; the rule was never the problem |
| Test failed to run | Environment or prerequisite issue | Not a detection finding |

The second row is where the two validation layers meet: an atomic run that fails becomes a permanent
unit-test case in `tests/rules/`, so the same failure cannot recur silently. See
[TESTING.md](TESTING.md).

## Refreshing the snapshot

```bash
python3 scripts/fetch_atomic_index.py
python3 scripts/build.py
make validate
git diff validation/atomic-index.json
```

Red Canary adds and withdraws tests regularly. Reviewing that diff is how you notice that a technique
you rely on gained a new variant.
